# My Bookings — the commit and minute tick, the card, the More menu, the next-class pill
Read this when you change `renderMyBookings`, a held class's buttons, the More menu, Find similar's popup or the floating next-class pill. Skip it for the card's shared surface ([class-card.md](class-card.md)) and for cancel logic ([booking.md](booking.md)).

**My Bookings commit + minute tick**: `renderMyBookings` ends in `_commitBookingsHtml(list, html, now)`, which skips the DOM write when the list on screen is already this HTML (state on the node: `_mbKey/_mbFirst/_mbAt`; countdown text is excluded from the key; every rendered button must be untouched or busy, else it rebuilds) — it must stay the LAST statement. One 60s timer in app.js (`_minuteTick`, stopped while hidden) updates `.mb-countdown[data-start]` and Discover's "Updated" label in place and re-renders My Bookings only when `_bookingsFlipDue` and the list is not in use; neither target may become an aria-live region. explore.js: every section write goes through `setHtml(el, html)`, and the sync banner is DRAWN from `_syncing/_syncLabel` (never a captured button; a silent top-up never paints it busy). tabs.js `getFullHistory` is memoised on the raw string (and coerced once through `_cleanStoredHistory`) — callers must not mutate the array.

**My Bookings card + More menu (Crisp Colour)**: the card keeps the class names the booking flows, the swipe and the suites read (`.book-btn.booked.mb-primary-btn`, `.booking-action-btn`, `.find-similar-btn`, `.up-seat-chip`, `class="mb-countdown"` + `data-start`, `.my-booking-card` LAST in the class list with `data-id` first) — a flow may rewrite a button's `className`, so css/crisp.css keys the buttons' look on WHERE they sit and on the card's state (`.is-late`, `.is-waitlisted`, `.glow-mine-card`), through the `.pill-btn` recipe's `--pill-fill / --pill-ink / --pill-line`. Its surface, glow, dashed place and meta line are the shared class card's (see The class card) — and "Leave waitlist", a pill with no line of its own, fills with that card's `--cc-pill`, so it steps a shade down at intensity `off` AND on Handheld (where, filled with the plain surface, it was invisible). Decisions are `pure:bookings-crisp` (nested inside a third `pure:bookings-card` region, so suites that load either get them; it must stay ABOVE `renderMyBookings` — nothing may sit between that function and `pure:render-perf`): `_mbShortDay` ("Thu 24", off the digits), `_mbActionPlan` (primary + ONE companion on the card; Add spot · Find similar · Map · Share behind More; nothing that spends or gives up a seat is ever in the menu; a lone overflow action goes on the card instead of a one-item menu), `_mbMoreName`, `_mbMoreKeyStep`, `_mbUsageModel` / `_mbUsageHtml` (a 27.5–31.5 day period is a "month", 6.5–7.5 a "week", anything else a "period"; ≤16 classes = one segment each), `_mbSpotsHeld` (what a held class uses of the plan: one booking PER SPOT — two bikes are 2, a studio with no spot map counts its records, a waitlist place 0; the rule of `_templateSeatsHeld`). THIS period's number is Psycle's own `bookings_made`; /profile says nothing about the NEXT period, so `renderMyBookings` adds up `_mbSpotsHeld` over the classes from `period_end` on (`inNextPeriod`, the one test behind both the split and the buckets) — counting classes there read "15 of 30 next month" over fifteen two-spot classes, a full month. The More menu is a DISCLOSURE, not an ARIA menu (the same buttons are inline at ≥1024px): `toggleBookingMore(btn)` flips `aria-expanded` — the ONLY thing the stylesheet shows the menu off — and sets `data-more-open` on the card (it rides over the next card); no class and no label changes, so `_commitBookingsHtml`'s "every button as we left it" check holds with a menu open. Focus moves to the first enabled item; Escape hands it back; arrows / Home / End step; a tap elsewhere on a card closes it and does nothing else; focus leaving closes it. One capture-phase click listener closes the menu BEFORE the chosen item's handler runs — except "Add spot" (`data-more-keep`: `bookClass` shows its "…" on that button, and the picker taking focus closes the menu). `_bookingsListBusy` and `_bookingsRepaintSafe` treat an open menu like the Similar popup. `.mb-more` comes LAST in the card's markup (pinned to the corner by CSS on a phone) so desktop reading order = focus order, and is a `.booking-actions` block so a touch on it never starts a swipe. `findSimilar` hangs its popup off the card's `.mb-actions` row (its own button may sit in a closed menu); the popup is a labelled group (`role="group"`, "Find similar") that TAKES focus on its first option — it lands before the More button in the markup, so Tab used to skip it — Escape closes it, and focus then goes to the card's visible trigger (the More button on a phone, Similar itself at ≥1024px); "Same class next week" hands focus back the same way before it searches. **Focus back from "Add spot"**: by the time the picker (or the last-seat / no-layout confirm) closes, the menu that holds "Add spot" has closed too (`display: none`), so `focus()` on the opener is a no-op; `_visibleOpener(el)` (`pure:sheets`, beside `confirmModal`) answers the menu's own More button instead, and both `_syncOverlayStack` and `confirmModal` restore through it. The next-class pill (settings.js `updatePill`) carries the class tile + seat badge. With no next class it is `.hidden` (a fade — it stays in the page), and a hidden pill is emptied: at once on `auth:changed` (it held the previous member's class), otherwise on the `updatePill` pass after the one that hid it (the 30 s tick at the latest), so the words are never seen to go. It steps aside while a list is read: `_pillScrollStep` (`pure:pill-scroll`) tucks it (`.is-tucked`: faded, slid down, `pointer-events: none` — a tap reaches the card under it) after 24px of travel DOWN, and brings it back after 8px UP, within 24px of the top or of the END of the list, and never changes it while a dialog is up (`_pillDialogUp` reads inline `display` off `[aria-modal]` ancestors — no layout). ONE capture-phase passive `scroll` listener, installed with the pill, counts only `.tab-content` (≤640px) or the document; one rAF per frame, one class write. Tucked it is still the same button — role, tabindex and name are `_pillA11y`'s alone — and focus un-tucks it (`_pillUntuck`, plus a `:focus-visible` rule as the net); reduced motion drops the slide and the fade. **At rest it never sits on a Book button either**: on a phone the top of a Discover day put the fourth card's Book under the pill's seat badge, and a tap there opened My Bookings (handing the tap on was rejected — the badge is what is drawn there, and a tap on it would have started a booking). Where the scroll always shows it (`dir` 0: the top, the end, a short list) `_pillRestCheck` measures the pill's resting box (`_pillBox`: layout size about the used `left` / `top`, so a tucked or hovered pill measures the same) against every enabled `.book-btn`, and while a button's CENTRE lies under it (`_pillCoversBook`, `pure:pill-rest`; an edge is left alone) it is drawn tucked — `_pillDraw`: scroll-tucked OR at rest on a button. The look is never taken in a scroll frame: the frame, a render (one `MutationObserver` on `body` → `_pillRendered`), a click, `animationend`, `resize` and the pill's `blur` all re-arm ONE 150ms timer (`_pillRestQueue`), and `updatePill` looks at once when it shows the pill (so it is never painted first) — every 30s, the net under the triggers. Standing aside is believed at once; coming BACK takes two clear looks 400ms apart (`_pillRestStep`; a render starts the count over) because cards and tab panels slide 8px into place and a look mid-slide blinked the pill on top of the button; arriving at the top / the end from a scroll-tuck it waits for the ONE look that follows. A scroll UP that calls it back (`_pillCalledBack`) keeps it whatever it lands on, and a pill under keyboard focus (`:focus-visible`; any focus where the engine lacks it) is never asked to stand aside. Apart from that, while it shows (`body.has-next-pill`) `#tab-bookings` ends `--tap-lg + --space-10` higher on phones, so at the end of the scroll the last card's actions are always clear of it (tests/suites/9d-bookings.js does the arithmetic).
